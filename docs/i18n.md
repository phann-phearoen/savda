# Internationalization (i18n)

## Scope

Applies to the landing page first; Shop (Next.js) will follow the same locale-prefix convention once built, using `next-intl` or equivalent.

## Strategy

- **Locale-prefixed routes**: `/en/` and `/km/`, each independently indexable (SEO requirement — matches the discovery-first goal in `docs/platform-concept.md`).
- **Default locale detection**: on first visit to `/`, detect browser/device language (`navigator.language` client-side, or `Accept-Language` header at the Nginx/edge layer if feasible) and redirect to `/en/` or `/km/`. Any locale not supported falls back to English.
- **Persistence**: once a visitor picks/lands on a locale, remember it via a cookie (e.g. `savda_locale`) so return visits and the language switcher don't re-trigger detection.
- **Language switcher**: always visible (e.g. header), lets a visitor override the detected/persisted locale at any time.

## Content structure

- Copy lives in per-locale JSON dictionaries: `apps/landing/content/en.json`, `apps/landing/content/km.json`.
- Both locale HTML pages are generated at build time from shared templates + these dictionaries (a small templating/pre-render step added to the landing's Vite build), not injected client-side — keeps each locale a fully-formed, crawlable static page with no flash-of-wrong-language.
- Shared, non-text content (images, layout, component structure) is not duplicated — only strings differ per locale.

## Fonts

- No conditional font-loading by locale — both `Kantumruy Pro` and `Manrope` subsets are small enough (~28 KB / ~66 KB, see `docs/typography.md`) to load on every page regardless of active locale, since a page can mix Khmer and Latin content (e.g. the សាវតា wordmark, brand names).
